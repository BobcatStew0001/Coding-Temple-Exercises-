 1. Making it more Pythonic

  The biggest change: stop numbering your variables. When you find yourself writing item1_…, item2_…, item3_… (and your own comment says "I also had to repeat it on these lines"), that usually means
  the data belongs in a list:

  items = [
      ("Notebook", Decimal("4.99"), 2),
      ("Pen Pack", Decimal("7.50"), 1),
      ("Backpack", Decimal("34.99"), 1),
  ]

  for name, price, qty in items:
      print(f"{name:<12}${price:>6} x {qty:<3}${price * qty:>8}")

  subtotal = sum(price * qty for _, price, qty in items)

  Now a fourth item is one new line instead of four lines plus edits to subtotal and the print section.

Other improvements:
  - float("4.99") → 4.99. Wrapping a literal string in float() or int() does nothing useful. Write the number directly. Converting makes sense for input() or file data, not for literals.
  - Use format specs for alignment instead of hand-typed spaces. {name:<12} left-aligns in 12 columns and {total:>8.2f} right-aligns in 8. This replaces the "trial & error" from your comment on
    line 36. Notice that line 36 currently has different spacing from lines 34–35.
  - Named constants: TAX_RATE = Decimal("0.075") and WIDTH = 30 in UPPER_CASE. Then the "Tax (7.5%)" label can come from the rate (f"Tax ({TAX_RATE:.1%})"), so the two can't disagree.
  - Typo: divder should be divider.
  - Wrap it in a main() with if __name__ == "__main__": main().

  2. Edge cases you're not handling

  - Long item names break the alignment. A name like "Graphing Calculator" pushes its columns past the others. Set a fixed width, or truncate with name[:12].
  - Negative or zero quantities and prices. Nothing stops qty = -1, which would print a negative total.
  - Empty cart. This can't happen with hardcoded items, but once you use a list it can. sum() handles an empty list fine, but you might want to print "No items" instead.
  - Rounding each line vs. rounding the total. Stores usually round tax once, at the end, to the nearest cent. Your printed lines are rounded for display but the math uses unrounded values. So with
    other prices, the printed subtotal plus printed tax can be one cent off the printed total.
  - Bad input later. If prices ever come from input() or a file, float("abc") raises ValueError, and you'd need try/except.

   3. Security and reliability concerns

  - Using float for money is the main reliability issue. Floats store values in binary, which can't hold most decimal fractions exactly. That's why your total is really 56.405249999999995, and why
    0.1 + 0.2 == 0.30000000000000004. It's harmless at this size but causes real cent errors in totals and comparisons at scale. Use decimal.Decimal, built from strings, and round explicitly:
    from decimal import Decimal, ROUND_HALF_UP
    tax = (subtotal * TAX_RATE).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
    This is the same idea as C#'s decimal type. Another common approach is to store whole cents as int.
  - Security: nothing to worry about yet, because there's no user input, file or network access. That changes once data comes from outside. Then you'd need to validate types and ranges, never pass
    input to eval(), and sanitize names if the receipt is ever written to HTML or a file.
  - The tax label and the tax rate are separate values, so one can be updated without the other. Building the label from the rate (above) fixes that.
